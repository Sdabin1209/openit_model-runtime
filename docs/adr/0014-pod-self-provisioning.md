# ADR 0014: 임대 파드가 스스로 환경을 준비한다 (uv 고정 + 독립 파이썬, 없을 때만 apt)

## 상태
채택(2026-10-28). 준비 단계(`--stage prereq`, `install`)는 PC의 Docker 이미지 3종에서 실제로 돌려 확인했다(결과: `docs/GPU_SESSION.md`). **RunPod 파드와 GPU 단계(`gpu`, `verify`)에서는 돌려 보지 않았다.** ADR 0013을 보완한다(0013 자체는 바뀌지 않는다).

## 맥락
이전 `pod_setup.sh`는 python3.12, gcc, `Python.h`가 없으면 중단했다. RunPod 파드는 템플릿마다 바탕 이미지(Ubuntu 22.04/24.04 등)와 설치된 패키지가 조금씩 다르다. 요구는 "이미지가 조금 달라서 키트가 안 도는 일이 없어야 한다"이다. 중단은 안전하지만 임대 시간에 사람이 고쳐야 한다. 제약: 파드는 이미 컨테이너라서 안에서 Docker를 쓸 수 없고, 기본 사용자가 root인 경우가 많지만 아닐 수 있으며, sudo는 쓰지 않는다. 모든 쓰기는 `--base` 아래(볼륨)다.

## 결정
1. **파이썬 3.12는 항상 uv가 받는 독립 파이썬(python-build-standalone)을 쓴다.** 시스템에 python3.12가 있어도 쓰지 않는다(`UV_PYTHON_PREFERENCE=only-managed`).
2. **uv는 버전(0.13.6)과 아키텍처별 sha256을 `pod_setup.sh`에 고정**하고 GitHub 릴리스 tarball을 받아 해시가 맞을 때만 `--base/uv`에 푼다. 루트 불필요, 설치 스크립트(`curl | sh`)는 쓰지 않는다. x86_64와 aarch64만 지원하고 그 밖은 중단.
3. **잠금 설치는 `uv pip install --no-deps --no-cache -r requirements-gpu.lock`**, venv는 `uv venv`.
4. **gcc, libc6-dev, curl, ca-certificates는 없을 때만, root일 때만 `apt-get install`로 설치**한다. root가 아니면 없는 것의 이름과 명령을 말하고 중단한다. `python3.12-dev`는 설치하지 않는다(독립 파이썬에 `Python.h`가 들어 있다). 헤더는 파일 유무가 아니라 **`Python.h`를 include한 C 파일이 실제로 컴파일되는지**로 확인한다.
5. **스크립트를 단계(`--stage gpu|prereq|install|verify|model|all`)로 나눈다.** 기본 `all`은 gpu -> prereq -> install -> verify -> model로 이전과 같은 순서다.

## 왜 (따른 표준과 근거)
- **독립 파이썬을 항상 쓰는 이유**: 시스템 파이썬에 기대면 이미지마다 경우가 갈린다(22.04는 3.12 없음, 24.04는 3.12가 있어도 `-dev`/`venv` 패키지 없을 수 있음, python 공식 이미지는 헤더 있음). 경우마다 분기하면 분기별로 시험해야 한다. 항상 같은 경로면 3개 바탕 이미지에서 같은 코드가 같은 순서로 돌고, 파이썬 패치 버전도 uv 버전이 정한다(재현성). 헤더와 `venv`가 포함돼 apt 의존이 gcc 하나로 줄어든다. 시스템 파이썬을 바꾸지 않는다.
- **uv 고정 tarball + sha256**: 공급망 표준 관행은 버전 고정과 해시 검증이다. astral은 릴리스마다 `*.tar.gz.sha256`을 게시하고 설치 스크립트도 버전 URL(`astral.sh/uv/<버전>/install.sh`)을 제공한다. 스크립트는 내려받아 실행하는 단계가 하나 더 있고 해시를 우리가 확인하지 못해, 해시를 직접 대조할 수 있는 tarball을 골랐다. 해시값은 같은 릴리스의 `.sha256` 파일에서 옮겼다(출처가 같은 릴리스라는 한계: 릴리스 자체가 탈취되면 못 잡는다. 그 위험은 감수).
- **uv가 받는 파이썬의 무결성**: uv 바이너리가 자신의 릴리스에 내장한 다운로드 메타데이터(sha256 포함)로 확인한다고 문서에 있다. 이 내장 동작을 우리가 따로 검증하지는 않았다.
- **`uv pip` + 잠금 파일**: 잠금 파일은 `==` 핀만 있는 pip 요구 형식이라 `uv pip install --no-deps -r`가 그대로 읽는다. 해석을 다시 하지 않는다(`--no-deps`). 설치 시간은 pip보다 짧을 것으로 기대하지만 **측정 안 함**(이전 pip 측정 2분 12초는 gpu-dev 값).
- **apt는 root일 때만**: apt는 시스템 패키지 관리의 표준이고 Ubuntu/Debian 계열 템플릿에 모두 있다. root가 아니면 시스템을 바꿀 권한이 없는 것이 정상이므로 우회(sudo, 소스 빌드)하지 않고 무엇이 필요한지 알려 멈춘다. `--no-install-recommends`로 최소만 설치.
- **단계 분리의 이유**: (1) GPU 없는 환경에서 준비 단계를 실제로 시험하려면 GPU 점검을 뺀 실행이 있어야 한다. 환경 변수나 "GPU 없으면 건너뜀" 분기는 파드에서 점검을 조용히 건너뛸 위험이 있어, 단계를 이름으로 명시하고 `all`만 파드 절차로 쓴다. (2) 실패한 단계만 다시 돌린다(임대 시간 절약). (3) 단계 사이 상태는 `--base` 아래 파일(uv, venv)뿐이라 순서 의존이 눈에 보인다.
- **점검 순서**: `all`에서 GPU 점검이 맨 앞인 것은 유지한다. GPU가 안 맞는데 uv와 파이썬을 받는 시간을 쓰지 않기 위해서다.

## 검토한 대안과 버리는 이유
- **템플릿을 고정하도록 요구(문서에 "이 템플릿만")**: 사용자 요구("조금 달라도 돈다")와 반대이고, 템플릿은 공급자가 바꾼다. 기각. 대신 CUDA 13 드라이버 같은 GPU 쪽 조건만 요구로 남긴다.
- **conda/miniconda**: 설치기가 수백 MB이고 채널 약관·solver가 따로 있으며 pip 휠 잠금과 이중 관리가 된다. uv는 단일 바이너리이고 PyPI 휠을 그대로 쓴다. 기각.
- **deadsnakes PPA 등 apt로 python3.12**: Ubuntu 22.04에서만 의미가 있고(PPA 추가는 root와 네트워크 의존, 배포판별 분기), 24.04/Debian은 다르다. 기각.
- **시스템 python3.12가 있으면 그것을 쓰고 없을 때만 uv**: 분기가 늘고 `-dev`/`venv` 부재를 또 처리해야 한다. 기각(결정 1).
- **컨테이너 안에서 Docker로 격리 실행**: 파드가 이미 컨테이너라 Docker 데몬이 없고 특권이 필요해 쓸 수 없다. 기각.
- **우리 이미지를 파드 템플릿으로 사용**: 이미지 게시·레지스트리 관리가 필요하고 임대 공급자 쪽 설정이 별도다. 이번 범위 밖. 되돌리는 조건 참고.
- **uv 설치 스크립트(`curl | sh`)**: 위 이유로 기각. **PyPI의 `pip install uv==...`**: 해시 고정은 가능하지만 pip와 `venv`가 있는 파이썬이 이미 필요해 닭과 달걀이다. 기각.

## 결과
- 얻는 것: 바탕 이미지가 달라도 같은 절차. 시스템 파이썬 상태 무관. 준비 단계를 GPU 없이 시험 가능(`tests/test_gpu_session.py` 단계·인자 시험, Docker 3종 실행).
- 감수하는 것: github.com 접근이 필요(uv와 독립 파이썬 출처). 독립 파이썬 내려받기 시간·디스크(측정치는 `docs/GPU_SESSION.md`). root가 아니고 gcc가 없으면 여전히 중단. uv 버전은 올릴 때 해시를 사람이 갱신해야 한다. glibc가 매우 오래된 이미지에서 독립 파이썬이 돌지 않을 수 있다(휠 `manylinux_2_31` 요건이 이미 더 엄격하다).
- 파드에서 처음 도는 것이므로 `gpu`/`verify` 단계와 RunPod의 실제 이미지는 미확인.

## 되돌리는 조건
- github.com이 파드에서 막히는 공급자를 쓰게 되면(미러 필요) 이 결정을 재검토한다.
- uv로 받은 파이썬에서 vLLM/Triton이 실제 GPU에서 실패하면 시스템 파이썬 경로로 되돌린다.
- 공급자가 CUDA 13 + python3.12 + gcc를 보장하는 고정 템플릿을 제공하면 단순화할 수 있다.
