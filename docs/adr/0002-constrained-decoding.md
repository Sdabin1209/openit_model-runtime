# ADR 0002: 제약 디코딩(xgrammar)과 완화 스키마(allOf를 anyOf로 펼침)

## 상태
채택(relax-3, 0.6.5, D83). 한계는 열려 있음(U14 보류).

## 맥락
모델 출력은 항상 `ActionExtraction` 스키마를 지켜야 한다. 그러나 계약 스키마는 `allOf`/`if-then`, `pattern`, `minItems` 같은 키워드를 쓰고 엔진(vLLM/xgrammar)이 모두 강제하지는 않는다. gpu-dev 측정(D82)에서 `allOf`는 경고와 함께 무시되고 `pattern`·`minItems`를 뺐더니 LoRA-A extract가 100% OUTPUT_INVALID였다.

## 결정
세 겹으로 보장한다: (1) 제약 디코딩으로 생성을 스키마에 가깝게 제한, (2) 항상 원본(완화 전) 스키마로 사후 검증, (3) 재시도(ADR 0007). 제약용 스키마는 `relax()`가 원본에서 기계적으로 만든다(사본 없음). relax-3는 `allOf`의 `if/then`을 같은 뜻의 `anyOf` 변형(action 8개, status 3개; 변형 상한 64)으로 펼쳐 xgrammar에 준다. 끝내 못 지키면 값을 지어내지 않고 503 `OUTPUT_INVALID`(D75).

## 왜 (따른 표준과 근거)
design.md 2(O14 결정), D82·D83. 원본 계약 스키마가 단일 정본이라 사본을 만들지 않는다(공통 규칙: 복사본 금지). 사후 검증이 항상 있으므로 제약이 약해도 잘못된 값이 조용히 통과하지 않는다. 동등성은 시험으로 확인했다(`tests/test_anyof_constraint.py`: 원본/변환 스키마 판정 등가, 1764건 전수 등). xgrammar 0.2.7에서 변환 스키마는 경고 없이 컴파일되고 유효 75건 수락, 위반 1895건 거부(CHANGELOG 0.6.5).

## 검토한 대안과 버리는 이유
- 제약 디코딩 없이 사후 검증+재시도만: 재시도 비용과 OUTPUT_INVALID 비율이 커진다고 판단했다는 기록은 있으나 **비교 측정은 없다(근거 기록 없음).**
- 계약 스키마를 엔진이 이해하는 모양으로 직접 고치기: 원본이 단일 정본이라 안 한다(D83 결정문).
- `values[].key`를 현재 문항의 유효 칸 집합으로 제한하는 문법(U14): 보류. 입력 형식이 학습 데이터로 고정(D74)이라 입력에 칸 목록을 넣을 수 없고, 하려면 서빙 API의 별도 매개변수로 문법에만 써야 한다. 학습된 LoRA-A는 키를 학습했고 서비스가 사후 검증(UNKNOWN_SLOT)으로 막는다.

## 결과
얻는 것: 형식 위반 대부분을 디코딩 단계에서 막는다. 감수하는 것: (a) 실제 vLLM·Qwen3·어댑터에서 재시도 없이 통과하는 비율, 문법 컴파일 시간·지연은 측정하지 않았다(CHANGELOG 0.6.5 '미확인'). (b) **U14의 한계: 학습 안 된 모델이 문항 세트에 없는 키를 지어내는 것은 제약이 못 막는다**(gpu-dev 1.7B 실험, OPEN_GAPS U07). 서비스 쪽 검증이 막는다. (c) `$` 앵커는 파이썬 `re`에서 끝 줄바꿈을 허용하므로 사후 검증기에서만 `\Z`로 읽는다(MR-14, `schema_guard.py`).

## 되돌리는 조건
xgrammar·vLLM이 `allOf/if-then`을 직접 지원하면 펼침을 줄이고 `supported_features`를 넓힌다(새 `relax_policy_version`). U14는 학습 안 된 모델로 데모를 통과시킬 필요가 생기면 그때 연다.
