# ADR 0004: 릴리스 번들 형식과 해시 검증

## 상태
채택(계약 소유는 boundary-contracts, 이 영역은 소비자).

## 맥락
모델은 release-gate(I4)를 통과한 릴리스로만 서빙한다. 서버가 번들(매니페스트, 문항 은행, 어댑터)을 스스로 읽어 적재하고, 변조·불일치는 적재 전에 걸러야 한다.

## 결정
`HttpReleaseReader`(boundary-contracts 클라이언트)가 `dest/<release_id>` 아래에 번들을 풀고 모든 해시를 검증한다. 서버는 추가로 `serving_config_hash`(정규화한 설정을 JCS로 직렬화해 SHA-256), 어댑터 디렉터리 해시, 패키지 시스템 프롬프트 파일의 `sha256`(D75), 문진 스키마 정수 버전, `model_runtime_version`의 MAJOR.MINOR를 확인하고 하나라도 다르면 그 릴리스만 FAILED로 한다. 서빙 중인 릴리스는 건드리지 않는다.

## 왜 (따른 표준과 근거)
해시와 직렬화는 계약의 기준 구현 `boundary_contracts.canonical`(RFC 8785 JCS)을 쓰고 직접 구현하지 않는다(HEAD 결정, design.md 10; CONVENTIONS 2절). 불일치는 조용히 넘기지 않고 오류 코드로 분류한다: 412 설정·사전조건, 422 버전·무결성, 503 I4 불가(HTTP.md 9절).

## 검토한 대안과 버리는 이유
- 해시 검증 없이 경로만 믿기: 변조를 못 잡는다. 기각.
- 자체 해시 구현: 이미 있던 자체 JCS 구현을 지우고 계약 구현으로 바꿨다(실수 직렬화를 직접 하지 않기 위해).

## 결과
얻는 것: 적재 실패가 그 릴리스에만 영향. 감수하는 것: 적재 때 디스크 쓰기가 필요하다(번들 디렉터리). 내려간 릴리스와 실패 적재의 번들 폴더는 지운다(0.7.3, MR-9). 소켓 timeout 기본 120s(`RELEASE_READ_TIMEOUT_S`)의 근거: **근거 기록 없음**(하드코딩된 값을 설정화만 했다. 번들 크기에 따른 측정 없음).

## 되돌리는 조건
계약(boundary-contracts)이 번들 형식을 바꾸면 따라간다. 이 영역이 독자적으로 바꾸지 않는다.
