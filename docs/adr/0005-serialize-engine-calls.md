# ADR 0005: 엔진 호출을 락으로 직렬화하고 대기가 길면 큐에 쌓지 않고 503

## 상태
채택. 직렬화 자체의 동기는 일부 '근거 기록 없음'.

## 맥락
여러 세션의 요청이 동시에 들어온다. HTTP.md I9는 '병렬로 처리하거나 짧은 대기열 뒤에서 처리하되, 대기가 호출 타임아웃(서비스 기본 4초)을 넘을 것 같으면 큐에 쌓지 말고 503'이라고만 정한다.

## 결정
`engine_lock` 하나로 엔진 호출을 한 번에 하나만 실행한다. 예상 대기(`(대기 중+1) x 이동평균 호출 시간`)가 `QUEUE_WAIT_S`(3.0s)를 넘으면 큐에 쌓지 않고 503. 요청마다 스레드(표준 라이브러리 `ThreadingHTTPServer`, ADR 0010)가 락을 기다린다.

## 왜 (따른 표준과 근거)
표준: HTTP.md I9의 위 문장(병렬 또는 짧은 대기열 둘 다 허용, 긴 대기는 503). 코드에서 확인되는 직접 이유: `ModelSession.last_call_info`가 세션 안의 공유 상태라서, 한 세션을 병렬로 부르면 호출 결과 메타데이터(`X-Openit-Outcome` 등)가 섞인다. 직렬화는 이 경쟁을 없앤다. vLLM 엔진 객체가 스레드 안전하지 않아서라는 이유는 **확인하지 못했다(근거 기록 없음).**

## 검토한 대안과 버리는 이유
- 병렬 처리(vLLM 연속 배칭 활용): 처리량은 늘 수 있으나 이 리포에서 시도·측정하지 않았다(근거 기록 없음). `max_num_seqs` 4/8은 프로파일에 있으나 서버가 동시에 넘기지 않는다.
- 무제한 큐: 호출자의 4초 timeout을 넘겨 응답이 의미 없어지므로 HTTP.md가 금지한다.

## 결과
얻는 것: 결과 메타데이터가 정확하고 대기 상한이 보장된다. 감수하는 것: 엔진이 병렬 가능해도 처리량이 직렬이다(키오스크 소수 동시 사용 가정, 측정하지 않았다). 동시 요청 부하는 미측정(OPEN_GAPS H4).

## 되돌리는 조건
실측으로 동시 환자 수가 직렬 처리량을 넘는 것이 확인되면 병렬 호출과 호출별 메타데이터 분리를 새 ADR로 한다.
