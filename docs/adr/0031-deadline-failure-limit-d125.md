# ADR 0031: 호출별 상한 extract 20.0초·respond 25.0초 (목표와 실패 판정 분리, ADR 0030의 값을 대체)

## 상태
채택(2026-11-02, 계약 CONVENTIONS '시간 상한 사슬' D125 개정판, 사용자 결정). Supersedes: [ADR 0030](0030-respond-deadline-5s.md)의 값(재시도 예산 규칙은 [0020](0020-per-call-deadline-budget.md) 그대로).

## 맥락
gpu-dev(RTX 4070, Qwen3-1.7B)에서 첫 환자 턴의 extract가 Triton JIT 컴파일로 3.0초를 넘겨 503 `ENGINE_TIMEOUT`이 났다(2026-11-02 실측). 사용자 지시: 2초는 목표이지 실패 판정이 아니다.

## 결정
`MODEL_RUNTIME_EXTRACT_DEADLINE_S` 기본 3.0 -> 20.0, `MODEL_RUNTIME_RESPOND_DEADLINE_S` 기본 5.0 -> 25.0(`DEFAULT_DEADLINES_S`). 합 45초 < survey 턴 마감 50초. 재시도 예산 계산은 이 값을 그대로 따라간다(코드 변경 없음). `QUEUE_WAIT_S` 3.0은 그대로다. 서버는 2초 목표를 강제하지 않는다. 패키지 버전은 올리지 않고 변경 이력에 적었다(설정 기본값).

## 왜
값의 정본은 계약 표다. 표의 근거는 표준 관행(프록시·LB 기본 60초)과 화면 응답 지침(Nielsen)이고 이 영역의 측정이 아니다. 우리 측정으로 근거를 댈 수 있는 것은 "3.0초는 첫 호출 JIT에 모자랐다"는 사실뿐이다. 새 값이 실제 모델(H1, 24GB)에서 충분한지는 측정하지 않았다.

## 검토한 대안과 버리는 이유
- 3.0/5.0 유지하고 적재 직후 예열 호출만 추가: 예열은 첫 호출 지연만 줄이고 그 밖의 정상 지연(느린 모델, 재시도)은 계속 장애로 판정한다. 목표와 판정을 나누라는 결정에 어긋난다. 예열은 별개 개선으로 남긴다(이번 범위 밖).
- 상한을 이 영역에서 따로 정하기: 정본이 둘이 된다. 기각.

## 결과
얻는 것: 정상 지연이 장애로 판정되지 않는다. 감수하는 것: 엔진이 멈추면 호출이 최대 20/25초 매달리고 그동안 `engine_lock`을 쥔다(요청 대기 상한 `QUEUE_WAIT_S` 3.0은 그대로라 뒤 요청은 3초 뒤 거절된다). 2초 목표 초과의 감시는 지표의 몫이다.

## 되돌리는 조건
계약 표가 바뀌면 `DEFAULT_DEADLINES_S`만 고치고 새 ADR로 대체한다.
