# 0015. 모델 이름의 출처는 프로파일 하나

## 상태
채택(2026-10-28). 0014(파드 자가 준비)를 보강한다. 0014를 대체하지 않는다.

## 맥락
`pod_setup.sh`의 `--model`(받을 모델, 기본 Qwen/Qwen3-8B)과 프로파일 `profiles/*.json`의 `base_model`(서버가 읽을 모델)이 따로 지정됐다. gpu-dev 실GPU 검증에서 둘이 어긋나면 `run_session`의 `HF_HUB_OFFLINE=1`에서 `LocalEntryNotFoundError`로 서버 기동이 실패했다. 모델 내려받기와 설치를 다 마친 뒤에야 드러나 파드 임대 시간을 낭비한다.

## 결정
- `pod_setup.sh`는 `--profile`(기본 `rtx4090-24g.json`, 이름이면 키트의 `profiles/` 아래, `/`가 있으면 그 경로)을 받아 그 `base_model`을 내려받을 모델로 쓴다.
- `--model`이 주어졌는데 프로파일의 `base_model`과 다르면 어떤 단계도 시작하기 전에 이유와 함께 종료 64로 중단한다. 같으면 허용한다. 프로파일이 없거나 `base_model`이 없어도 중단한다.
- 우회 옵션은 두지 않는다. 다른 모델이 필요하면 프로파일을 바꾸거나 맞는 프로파일을 `--profile`로 준다.
- `pod_run.sh`는 자신이 세션에 쓰는 `$PROFILE`(기본 같은 `rtx4090-24g.json`, `--profile`로 변경)을 `pod_setup.sh --profile`에도 넘긴다. 두 스크립트의 기본값이 같다.

## 왜
- 한 사실은 한 곳에서만 쓴다(워크스페이스 규칙). 모델 이름은 이미 프로파일이 서버 쪽 출처이므로, 받는 쪽이 그것을 읽게 하면 어긋날 수 없다.
- 실패는 시작 전에 값싸게 잡는다. 어긋남을 파드 위에서 모델을 받은 뒤 서버 기동에서 발견하면 임대 비용이 이미 나간 뒤다(0014의 '비용 전에 중단' 원칙과 같다).
- `base_model` 읽기는 `sed` 한 줄이다. prereq 단계에는 venv도, 가정할 시스템 파이썬도 없기 때문이다. 프로파일은 `"base_model": "..."`를 한 줄에 두는 형식이며, 시험이 4개 프로파일 모양과 이 읽기를 확인한다(다른 모양으로 쓰면 'base_model이 없다'로 중단하므로 조용히 틀리지는 않는다).

## 검토한 대안과 버리는 이유
- **`--model` 유지 + 문서로 맞추기**: 사람이 맞춰야 하는 구조는 이번처럼 다시 어긋난다. 기각.
- **불일치를 경고만 하고 진행 / 강제 옵션(`--force-model`)**: 어긋난 채 진행하면 같은 기동 실패로 이어진다. 의도적으로 다른 모델이면 프로파일을 바꾸는 것이 맞다. 기각.
- **`--model` 제거**: 기존 호출·문서와의 호환이 깨진다. 확인용으로 남긴다.
- **파이썬으로 JSON 파싱**: prereq 전에는 사용할 파이썬이 없다. 기각.

## 결과
- 얻는 것: 받은 모델과 서버가 읽을 모델이 구조상 같다. 어긋남은 시작 전에 이유와 함께 멈춘다.
- 감수하는 것: 프로파일의 `base_model` 한 줄 형식에 의존한다. 기반 모델 이름을 바꾸려면 프로파일 수정이 필요하다.
- 실제 파드에서 돌려 보지는 않았다(PC에서 시험만; `tests/test_gpu_session.py`).

## 되돌리는 조건
프로파일이 `base_model` 외의 모델(예: 어댑터별 다른 기반)을 여러 개 요구하게 되면 모델 목록을 프로파일에 두는 방식으로 대체한다(새 ADR).
