# ADR 0006: 요청 총 상한 3.5초와 대기 상한 3.0초

## 상태
호출 하나 3.5초 부분은 [ADR 0020](0020-per-call-deadline-budget.md)이 대체한다(2026-10-29, 계약 2.2.0). 대기 3.0초와 나머지는 유효. 원래 상태: 채택(초기값). **실제 모델 지연으로 측정한 적이 없다.**

## 맥락
멈추거나 매우 느린 엔진 호출을 무한히 기다리면 호출 스레드와 락이 영구히 묶이고 `/readyz`도 200이었다(FAULT_MATRIX A4 F2). 호출자 쪽에는 시간 불변식이 있다: 키오스크 대기 10s > gateway 9.5s > survey 턴 마감 6s > survey의 model-serving 읽기 timeout 4s(FAULT_POLICY 3, 4항).

## 결정
`MODEL_RUNTIME_REQUEST_DEADLINE_S` 기본 3.5(대기+추론+재시도 3회를 합친 요청 총 상한. 넘으면 503 `ENGINE_TIMEOUT`), `MODEL_RUNTIME_QUEUE_WAIT_S` 기본 3.0(상한에 포함). 엔진 호출은 스레드에서 계속되고 끝나면 락이 풀린다. 그동안 `/readyz`는 503, `/healthz`는 200.

## 왜 (따른 표준과 근거)
표준: FAULT_POLICY 원칙 4(의존이 응답하지 않을 때 무한히 기다리지 않는다. 값은 설정으로 두고 기본값과 근거를 영역 문서에 적는다)와 위 불변식(서버 상한은 survey의 4초 읽기 timeout보다 짧아야 서버가 먼저 분류된 503을 낸다). 3.5는 4보다 작다는 제약에서 나온 값이고, 3.0은 HTTP.md의 '호출 타임아웃(4초)을 넘을 것 같으면 503'보다 작게 둔 값이다. 3.5 대 3.0 대 0.5초 여유의 구체적 선택 근거: **근거 기록 없음**(측정 아님, 가짜 백엔드·1.7B 측정 중앙값 약 1.7초를 참고했을 뿐이다).

## 검토한 대안과 버리는 이유
- 상한 없음(기존): 위험. 기각.
- 호출별 소켓 timeout 합: 재시도가 합쳐져 총 상한을 못 지킨다. 총 상한으로 건다(FAULT_POLICY 3).
- 엔진 호출 강제 중단: 파이썬 스레드는 중단할 수 없다. 엔진이 영영 안 돌아오면 프로세스 재시작은 밖(스케줄러/운영자)이 `/readyz` 503 지속을 보고 한다(`/healthz`는 정책상 200).

## 결과
얻는 것: 무한 대기 제거, 분류된 오류. 감수하는 것: **8B 모델(24GB)에서는 호출 하나가 3.5초를 넘어 `ENGINE_TIMEOUT`이 날 수 있다**(미측정). 한 환자 턴은 extract와 respond 두 번 호출하고 survey 턴 마감은 6초다.

## 되돌리는 조건
H1(24GB 실측)에서 extract·respond 각각의 p50/p95/max를 재서 정한다(절차는 docs/boundary.md '실측 절차'). 그 전까지 이 값은 초기값이다.
