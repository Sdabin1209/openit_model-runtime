# ADR 0022: 추론 서버를 WSGI 앱 + waitress로 (ADR 0010 대체)

## 상태
채택(2026-10-29, 헤드 지시 단위 4a, D111). [ADR 0010](0010-stdlib-http-server.md)을 대체한다.

## 맥락
ADR 0010은 `http.server.ThreadingHTTPServer`를 쓰고 연결 상한(`BoundedServer`), 소켓 timeout, 본문·Content-Length·Transfer-Encoding 검증, 우아한 종료를 직접 구현했다. 표준 점검(2026-10-29)이 이를 "웹 서버가 제공하는 영역을 직접 만듦"(O)으로 분류했고, 파이썬 문서는 `http.server`가 기본 보안 검사만 한다고 경고한다.

## 결정
1. HTTP 계층을 **waitress 3.0.2**(순수 파이썬 WSGI 서버)에 맡기고 서비스는 **WSGI 앱**(PEP 3333) `make_app(svc)`로 둔다. 앱은 경로·인증·본문 검사·응답 모양만 안다.
2. `make_server`의 설정과 값의 출처:
   - `threads = connection_limit = MODEL_RUNTIME_MAX_CONNECTIONS`(기본 32): **제약+초기값**. 추론 요청 하나는 엔진 직렬화 락을 기다리며 스레드를 최대 호출 상한(3.0초)까지 쥔다. 스레드가 연결보다 적으면 `/healthz`가 그 뒤에 줄을 선다. 32는 ADR 0012의 기존 값이고 부하는 **측정하지 않았다**.
   - `channel_timeout = ceil(MODEL_RUNTIME_CONN_TIMEOUT_S)`(기본 15초, 최소 1): 값 15는 **ADR 0012의 초기값, 측정·표준 근거 없음**. waitress가 정수 초만 받는다. 유휴이거나 요청을 끝내지 않은 연결(slowloris 모양)을 닫는다.
   - `cleanup_interval = 1`: **제약**. 기본 30초면 연결이 timeout보다 최대 30초 늦게 닫힌다. 1초는 timeout의 정밀도를 1초로 하자는 선택이고 비용(주기적 순회)은 측정하지 않았다.
   - `max_request_body_size = MAX_BODY`(4MiB): ADR 0012의 값, 4MiB 근거 기록 없음.
   - 나머지는 waitress 기본값이다(백로그 1024, 헤더 크기 한도 등). 기본값을 따르는 이유: 표준 도구의 기본이 직접 정한 값보다 검증된다. 이 서비스의 부하에서 맞는지는 측정하지 않았다.
3. 우아한 종료: SIGTERM/SIGINT 핸들러가 `SystemExit`을 올리면 waitress의 `run()`이 새 연결을 그만 받고 진행 중인 작업을 마친 뒤 돌아온다. 이어서 기존 `SHUTDOWN_GRACE_S`까지 `svc.pending`을 기다리고 엔진을 내린다.
4. 엔진 직렬화 락(ADR 0005)과 호출별 시간 예산(ADR 0020)은 서비스 객체 안에 그대로 있다. 서버 교체와 무관하다.

## 왜 (따른 표준과 근거)
- 따른 표준: **PEP 3333**(WSGI). 앱이 표준 인터페이스라 서버를 바꿀 수 있다. 워크스페이스 D111(직접 만든 인프라를 표준 도구로).
- waitress를 고른 이유: 이 서비스는 단일 프로세스·다중 스레드 설계(엔진을 프로세스 안에 하나만 올린다, ADR 0001/0005)다. gunicorn 같은 prefork 서버는 워커마다 엔진을 올리게 되어 맞지 않는다. waitress는 단일 프로세스 스레드 풀 서버이고 순수 파이썬이라 GPU 이미지에 네이티브 의존을 더하지 않는다.

## 검토한 대안과 버리는 이유
- gunicorn(prefork): 워커마다 엔진 적재. 기각.
- uvicorn/ASGI + 프레임워크: 앱이 동기 코드이고 엔진 호출이 블로킹이라 이득이 없다. 새 프레임워크 의존이 크다. 기각(성능 비교는 하지 않았다).
- 현 상태 유지: 점검의 O 항목이 남는다. 기각.

## 결과
얻는 것: 연결·timeout·본문 상한·keep-alive·chunked 해석을 검증된 서버가 한다. 직접 만든 서버 코드가 사라졌다(`BoundedServer`, 핸들러 서브클래스).
감수하는 것(동작 변화, 시험으로 고정): (1) 연결 상한 초과는 503이 아니라 대기, (2) 본문 상한 초과는 413과 waitress의 오류 본문, (3) 잘못된 Content-Length는 waitress의 400 본문, (4) 토큰 끝 공백 제거와 헤더 이름 대문자화. 본문 상한 413은 계약 CONVENTIONS 9절(2.2.2)이 전송 계층 한도로 정의하고 계약 클라이언트가 INVALID_RECORD로 읽는다. 연결 상한 대기가 이웃에 닿는지는 이웃을 읽지 않아 **미확인**이다. 연결 상한 초과 시 클라이언트가 503 재시도 대신 읽기 timeout(4초)에 걸릴 수 있다.

## 되돌리는 조건
부하 측정에서 스레드 32가 과하거나 모자라면 값을 바꾼다. 연결 상한의 503 거절이 계약으로 요구되면 앞단 프록시에서 한다.
