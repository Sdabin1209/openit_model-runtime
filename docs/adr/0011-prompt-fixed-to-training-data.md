# ADR 0011: 프롬프트 입력 형식을 학습 데이터에 고정한다(prompt-4)

## 상태
채택(D74, D77). 시스템 프롬프트는 모델 패키지의 일부(D75).

## 맥락
LoRA는 특정 입력 글자 분포로 학습된다. 서빙 입력이 학습 글자와 다르면 품질이 떨어진다.

## 결정
채팅 형식은 Qwen3 ChatML에 `enable_thinking=False`. 사용자 메시지는 `json.dumps(입력 객체, ensure_ascii=False)`(기본 구분자)로, A는 최상위 키만 사전순, 그 아래는 호출자 순서를 보존하고, B는 전 수준 사전순이다. `render_prompt`는 학습 변환과 서빙이 같은 함수를 쓴다. 템플릿 버전은 `prompt-4` 하나다.

## 왜 (따른 표준과 근거)
D77: 학습 서버 val(A 400행, B 300행)에서 학습 데이터의 user 메시지가 위 직렬화와 글자 단위로 같음을 확인했다(`scripts/check_prompt_matches_dataset.py`). 시스템 프롬프트는 패키지 파일이며 해시로 고정된다(D75). 서버가 최상위 키 순서를 강제하는 이유는 호출자 구현마다 순서가 달라 글자 어긋남이 생기기 쉬워서이고, `state` 안의 순서는 학습 때 삽입 순서라 복원할 수 없어 호출자 책임이다(prompts.py docstring).

## 검토한 대안과 버리는 이유
- JCS(`prompt-3`): 학습 글자와 다르다. 0.7.0에서 제거(G10).
- 입력에 칸 목록 등을 더 넣기: 입력 형식은 학습 데이터로 고정(D74)이라 불가(U14와 같은 이유).
- 특수 토큰 이스케이프: 입력 문자열에서 `<`+(`|`,`/`,영문자,`_`) 앞에 공백을 넣고 `|>`를 `| >`로 바꿔 채팅 특수 토큰을 깬다(MR-2, 0.7.3). 자연스러운 한국어 발화에는 이런 문자열이 없다고 보고(학습 데이터 전수는 확인하지 못했다) 학습 분포를 해치지 않는다고 판단했다. 이 처리는 `render_prompt` 안이 아니라 서버 입구에 둔다(학습 변환·평가 경로를 바꾸지 않으려고).

## 결과
얻는 것: 서빙과 학습의 글자 일치. 감수하는 것: 호출자(survey-service)가 입력 키 순서를 학습 규칙대로 만들어야 한다. 실제 토크나이저가 텍스트 안의 특수 토큰 문자열을 특수 토큰으로 해석하는지는 GPU 환경에서 확인하지 못했다(방어는 해석 여부와 무관하게 안전하다).

## 되돌리는 조건
학습 데이터 형식이 바뀌면(새 데이터셋·새 `prompt` 버전) 새 템플릿 버전과 새 ADR.
