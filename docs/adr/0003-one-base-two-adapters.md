# ADR 0003: 한 기반 모델에 LoRA-A·LoRA-B를 동시에 올리고 요청별로 고른다

## 상태
채택. 12GB 동시 적재는 간접 확인뿐(미확인).

## 맥락
문진 서비스는 두 역할을 쓴다: A는 발화에서 값을 추출하고(extract), B는 환자에게 할 문장을 만든다(respond). 어댑터는 기반 모델에 묶여 다른 기반 모델로 옮길 수 없다(brief GPU 규칙).

## 결정
기반 모델 하나를 엔진에 올리고 두 LoRA 디렉터리를 요청별로 붙인다(`max_loras: 2`, `max_lora_rank: 16`은 학습 어댑터 rank 16과 같다, D74). 릴리스 교체는 새 `release_id`로 PUT 적재하고(멱등) 이전 릴리스를 `MAX_RELEASES`(4)까지 유지한다. 어댑터와 프로파일의 기반 모델이 다르면 엔진 전에 412로 거부한다.

## 왜 (따른 표준과 근거)
design.md 2.1 근거 (1): `load`가 어댑터 경로를 받고 한 기반 모델에 두 어댑터를 올리는 구조가 맞다. GPU 메모리는 기반 모델 가중치를 한 번만 쓰면 된다는 점이 12/24GB 목표에 맞는다(이 추론 자체는 측정하지 않았다). 릴리스를 4개까지 두는 값의 근거: **근거 기록 없음**(롤백용 여유로 추정, 측정·표준 없음).

## 검토한 대안과 버리는 이유
- 역할마다 별도 모델 프로세스: 가중치가 두 배로 든다는 이유를 들 수 있으나 이 리포에 비교 기록은 없다(근거 기록 없음).
- 어댑터를 병합한 모델 두 개: 병합 방식·결과 비교 기록 없음.

## 결과
얻는 것: 메모리 절약, 릴리스 교체가 어댑터 교체로 끝난다. 감수하는 것: gpu-dev 12GB에서 A·B 동시 적재는 B respond 200과 A extract 생성이 된 것으로만 간접 확인했고 어댑터 로드 성공 로그는 찾지 못했다(`two_adapters_loaded_together: unverified`). 동시 요청 부하·장시간 안정성은 미확인.

## 되돌리는 조건
동시 적재가 실제로 안 되거나 지연이 요건을 못 맞추면 역할별 프로세스로 나누는 안을 새 ADR로 비교한다.
